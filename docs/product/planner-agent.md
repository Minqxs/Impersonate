# Planner agent

The planner converts one project-scoped feature request into a bounded ordered plan. Planner v2 input contains project metadata, the request, configured limits, prompt version, a deterministic repository tree, bounded safe excerpts, and a clearly named `allowedRepositoryEvidencePaths` list. It contains no secrets, unrelated projects, personality data, hidden model reasoning, Git metadata, binary content, or absolute workspace paths.

Output is strict JSON with summary, `canPlan`, notes, tasks, or a failure reason and clarifying question. The application validates contiguous ordering from one, unique concise titles, descriptions, meaningful acceptance criteria, placeholder wording, unsupported execution or repository-inspection claims, and maximum count before persistence. Invalid tasks are never persisted. Validation is a structural safety boundary, not proof that a plan is technically perfect.

`repositoryEvidence` is optional supporting metadata. Every value must be copied exactly from `allowedRepositoryEvidencePaths`; directories, globs, inferred or shortened names are invalid, and `[]` is correct when no supplied file directly supports the task. Slash direction and a leading `./` are normalized and mapped back to the canonical snapshot path, with case-insensitive comparison for Windows-compatible Git paths. There is no fuzzy filename matching.

The Worker retains each attempt and retries only to the configured finite limit. Invalid output produces bounded structured correction context containing exact safe offending paths, suitable allowed paths, and a bounded previous plan so valid fields can be corrected rather than regenerated. On the final attempt, unsupported evidence alone may be removed when the core plan and dependency structure are valid; the run records a planning warning and audit event and never persists fabricated evidence. Cycles, missing dependencies, sequence errors, missing acceptance criteria, placeholders, false execution claims, malformed output, and all other structural failures remain blocking. A successful plan becomes `ReadyForExecution`; ambiguity becomes `WaitingForClarification`; exhaustion becomes `Failed`.

Safe readiness reports whether provider, model, and credentials are configured before the user starts planning. The API remains authoritative and the Worker idles when its matching configuration is incomplete. Run details display attempt status, safe failure category, provider/model metadata, and prompt version without exposing credentials.

For connected providers, project-scoped routing readiness supersedes that legacy environment check. Created run details preview the selected provider, model, source, and explanation for the actual feature request. Start Planning is enabled by a successful preview; its backend operation remains authoritative and persists the final choice before Worker execution.
